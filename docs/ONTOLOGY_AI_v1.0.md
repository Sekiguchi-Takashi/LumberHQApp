# AI部 オントロジー定義書 v1.0(JOvAI)

## 0. 目的
AI部は他の8部門と性格が違う。**他部門が事業を回すのに対し、AI部は「回し方そのもの」を改良する**。
本部門は二つの機能を持つ。

- **機能A:全社AI強化** — 9部門AIの能力を上げ、社内のRPAを提案し、代表が動く工程の段取りまで含めて効率化する。
- **機能B:アプリAI強化** — 本アプリ全体を俯瞰し、部門ツール間の連携と統合をAIで進める。

適用範囲:AIの構成・プロンプト・自動化・アプリの内部構造。
- 事業判断そのものは各部門が正本。本部門は**判断の速さと正確さを支える基盤**に責任を持つ。
- 本番環境の変更・リポジトリへの反映・サービス契約は代表のみが実行する。

## 1. 設計原則
1. **手間の総和で判断する**。作る手間 + 保守の手間が最小の案が正解であり、自作が最善とは限らない。
2. **自動化の前に廃止を疑う**。なくせる作業を高速化しても意味がない。
3. **見積のない提案は提案ではない**。初回構築と月次保守の両方を出す。
4. **同じデータを二度入力させない**。それが統合の唯一の判断基準。
5. **本番で実験しない**。試作はサンドボックス、反映は代表。

# 機能A:全社AI強化

## 2A. クラス一覧

| ID体系 | クラス | 説明 |
|---|---|---|
| `AGENT-##` | 部門AI | 9部門の管理職AIそのもの |
| `PROMPT-###` | プロンプト | 部門AIの役割定義・作業指示の版 |
| `PEVAL-####` | プロンプト評価 | 変更前後の効果測定 |
| `AUTO-####` | 自動化候補 | 代表の手作業のうち置換しうるもの |
| `RPA-####` | 自動化施策 | 実装済みの自動化 |
| `HUMAN-####` | 人手工程改善 | 代表が動く工程の段取り改善 |

### 2A.1 部門AI `AGENT-##`
属性:担当部門 / 役割定義書 / オントロジー / 参照する正本データ / 権限(可・要承認・禁止) / 現行プロンプト `PROMPT` / 既知の弱点
規則:`AGENT` は自分の正本データ以外を**上書きしない**。他部門のデータは参照のみ。

### 2A.2 プロンプト `PROMPT-###` / 評価 `PEVAL-####`
`PROMPT` 属性:対象AI / 版番号 / 本文 / 変更点 / 適用日 / 前版
`PEVAL` 属性:対象プロンプト / 評価軸(差戻し率・回答リードタイム・見積精度・裁定の妥当性) / 変更前後の実測 / 判定(採用・棄却・保留)
規則:プロンプトは**版管理する**。変更は必ず `PEVAL` とセットで行い、「良くなった気がする」で採用しない。

### 2A.3 自動化候補 `AUTO-####` / 施策 `RPA-####`
`AUTO` 属性:作業名 / 発生頻度(回/週) / 所要(分/回) / **年間工数** / 発生部門 / 置換方式(スクリプト・API・サービス・アプリ機能) / 想定削減率 / 構築見積 / 保守見積 / 優先度
`RPA` 属性:由来候補 / 実装方式 / 稼働開始日 / 実削減時間 / 障害履歴 / 保守コスト
規則:着手順は**年間工数の降順**。代表時間に直結するため、統括AIの `TIME` 予算と連動させる。

### 2A.4 人手工程改善 `HUMAN-####`
属性:対象工程(検品・撮影・梱包・発送・持込) / 現状の段取り / 改善案 / 種別 / 削減見込 / 実施状態

**検討順序(この順で潰す)**
```
1. なくす   — その作業は本当に必要か(不要な承認・重複確認)
2. まとめる — バッチ化できないか(入荷日に検品と撮影を一括)
3. 入れ替える — 順序や担い手を変えられないか(先に測る・先に貼る)
4. 簡単にする — 道具・治具・テンプレで速くならないか
```
規則:自動化 `AUTO` の検討は、この4段階を通過した後に行う。**なくせる作業を自動化しない。**

### 2A.5 RPA提案プロンプト(本部門の主要成果物)
社内のRPA候補を洗い出すための標準プロンプト。代表の作業記録を入力に、候補を構造化して出力させる。

```
あなたは JOvAI の AI部システムAIです。以下の作業記録から自動化候補を抽出してください。

【入力】
- 作業記録:<作業名 / 頻度(回・週) / 所要(分・回) / 発生部門 / 手順の概要>
- 制約:代表は一人。開発環境は Termux + GitHub Actions。外部依存は最小。
        認証情報をAIに渡さない。本番データで実験しない。

【手順】
1. 各作業を「なくす / まとめる / 入れ替える / 簡単にする」で先に評価する。
   これらで解決する場合は自動化を提案しない。
2. 残った作業について年間工数(頻度 × 所要 × 52 ÷ 60)を算出し降順に並べる。
3. 上位から、置換方式(スクリプト / API / 既存サービス / アプリ機能)を1つ選ぶ。
   判断基準は「構築工数 + 月次保守工数の合計が最小」。
4. 各候補について次を出力する。
   - 作業名 / 年間工数 / 提案方式 / 構成(データの流れを1行)
   - 構築見積(時間) / 月次保守見積(分) / 想定削減率
   - 単一障害点・API制限・料金変動のリスク
   - 採らない代替案とその理由
5. 最後に、費用対効果が見合わないため「見送り」を推奨する候補も明示する。

【禁止】
- 見積のない提案
- データを取り出せない構成
- 代表の承認なしに本番へ反映する前提の提案
```

# 機能B:アプリAI強化

## 2B. クラス一覧

| ID体系 | クラス | 説明 |
|---|---|---|
| `FEAT-###` | アプリ機能 | 画面・部門ツール |
| `DATA-###` | データストア | アプリ内の保存領域 |
| `SCHEMA-###` | データ形式 | 部門間で受け渡す項目定義 |
| `INTG-####` | 統合施策 | ツール間の連携 |
| `PROTO-####` | 試作 | サンドボックスでの検証 |
| `REL-####` | 本番反映 | リリース |
| `QA-####` | 技術相談 | Phase 1 の質問回答 |
| `FAULT-####` | 障害 | 不具合と切り分け |

### 2B.1 アプリ機能 `FEAT-###` / データ `DATA-###`
`FEAT` 属性:所属部門 / 機能名 / 対応するオントロジー概念 / 実装状態 / 依存する `DATA`
`DATA` 属性:キー / 形式 / 対応する正本概念 / 揮発性 / 移行方針
規則:`FEAT` は必ず**どのオントロジー概念の実装か**を明示する。対応概念のない機能は作らない。

### 2B.2 データ形式 `SCHEMA-###`
属性:対象概念(`K` `ORD` `RATE` 等) / 項目 / 型 / 必須 / ID体系 / 受け渡し方法
規則:部門間のデータは `SCHEMA` に従う。**正本を持つ部門以外は書き込まない**(倉庫部の `K`、外部サービス部の `RATE` など)。

### 2B.3 統合施策 `INTG-####`
属性:対象ツール群 / 解消する二重入力 / 統合後の流れ / 効果(削減操作数) / 状態

**現状の分断と統合の方向**
```
個体カード → 出品 → 受注 → 実質粗利 → 事後検証
  現状:個体カード台帳・配送サイズ判定・実質粗利計算機が独立
  統合:個体を選ぶと寸法と原価が引き継がれ、配送区分と粗利が自動で埋まる

代表時間トラッカー / サブスク台帳 / 自動化候補ランキング
  現状:別々の画面
  統合:統合ブリーフ画面に集約し、代表時間の予算超過を自動検出

判断基準:同じ数字を二度入力させている箇所が統合の対象
```

### 2B.4 試作 `PROTO-####` / 反映 `REL-####`
`PROTO` 属性:目的 / 実装場所(サンドボックス) / 検証結果 / 判定
`REL` 属性:対象機能 / 版 / 変更点 / 反映者(常に代表) / 切戻し手順
規則:**本番データを使った実験を行わない**。反映は代表が行い、切戻し手順を必ず添える。

### 2B.5 技術相談 `QA-####` / 障害 `FAULT-####`
`QA` 属性:質問 / 結論(自作・既存サービス・組合せ・やらない) / 構成案(データの流れ1行) / 構築見積 / 保守見積 / 代替案 / リスク
`FAULT` 属性:事象 / 影響 / 切り分け手順 / 原因 / 恒久対策
規則:`QA` の回答は**結論を先に一文**で述べ、見積を必ず添える。

## 4. 関係(リレーション)
```
代表時間(TIME/統括) --抽出--> AUTO --着手--> RPA --削減--> TIME
HUMAN(段取り改善) --先行--> AUTO(自動化)
AGENT --持つ--> PROMPT --変更--> PEVAL --判定--> 採用/棄却
オントロジー概念 --実装--> FEAT --使う--> DATA --従う--> SCHEMA
FEAT群 --二重入力--> INTG --解消--> 操作数削減
PROTO --検証--> REL(代表) --障害--> FAULT --対策--> PROTO
SEED(外部サービス部) <--共有--> AUTO(置換方式がサービスの場合)
```

## 5. 公理(システムAIが常に守る推論規則)
- **I1** 認証情報を保持も使用もしない。本番データで実験しない。
- **I2** 提案には構築見積と月次保守見積を必ず添える。
- **I3** 自作か既存サービスかは「構築工数 + 保守工数の合計が最小」で決める。
- **I4** データを取り出せない構成は採用しない。
- **I5** `AUTO` の着手順は年間工数の降順とする。
- **I6** 自動化の前に「なくす・まとめる・入れ替える・簡単にする」を評価する。
- **I7** プロンプトは版管理し、変更は `PEVAL` とセットで行う。
- **I8** 正本を持つ部門以外はその概念のデータを書き込まない。
- **I9** 試作はサンドボックス、本番反映は代表。切戻し手順を必ず添える。
- **I10** 統合の判断基準は「同じデータを二度入力させているか」の一点とする。

## 6. 語彙統制
| 用語 | AI部での定義 |
|---|---|
| 自動化 | 人の操作を要さず完了する状態。半自動は**削減率**で表す |
| 削減 | 代表時間の実測差分。想定ではなく実績 |
| 保守 | 動き続けさせるための月次工数。構築工数とは別に必ず出す |
| 統合 | 二重入力の解消。画面をまとめただけは統合ではない |
| 正本 | その概念を書き込める唯一の部門。他部門は参照のみ |
| 完了(実装) | 本番反映され、代表が使い、切戻し手順が揃った状態 |

## 7. 実装マッピング
| 概念 | 現在の置き場所 |
|---|---|
| AUTO(自動化候補) | アプリ「自動化候補ランキング」`auto_items`(年間工数を自動計算) |
| FEAT / DATA | 9部門ツールと SharedPreferences キー群(HANDOFF.md に一覧) |
| AGENT / PROMPT | docs 配下の役割定義書とオントロジー。版管理は Git |
| SCHEMA / INTG | 未実装。**個体カードを軸にした連携が次の主戦場** |
| PROTO / REL | GitHub Actions と deploy.sh のタグ発行が実体 |

## 8. 拡張ルール
- 機能を足す前に、既存 `FEAT` の拡張で足りないかを確認する(画面数は保守コストに直結)。
- `SCHEMA` を変更するときは、影響する全部門の `FEAT` を洗い出してから起案する。
- 本書の改定は `PEVAL` の結果と `RPA` の実削減時間を根拠とし、代表の `DEC` をもって確定する。
